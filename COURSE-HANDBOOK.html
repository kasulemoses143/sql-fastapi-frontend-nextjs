PostgreSQL FastAPI TypeScript and Next.js

A complete guided build for Python learners: design a PostgreSQL database, create and deploy a FastAPI CRUD backend, learn TypeScript from first principles, build a React interface with Next.js and Tailwind, connect the existing API, and deploy the complete application on Vercel.

The material works for self study and tutor-led teaching. It contains 48 sequential lessons, complete source examples, installation procedures, expected results, exercises with answers, assessments and recovery checkpoints. No previous JavaScript or TypeScript experience is assumed. Advance after passing each result check.

Follow this order

  1. Read how to use the course.
  2. Follow installation and accounts.
  3. Start Lesson 01, using the full contents.
  4. Tutors use the scheme of work and assessment guide.
  5. Consult API and relational design, testing, deployment and troubleshooting at the directed checkpoints.

The system you build

Browser
  → TypeScript React frontend using Next.js on Vercel
  → Python FastAPI backend on Vercel
  → PostgreSQL operated by Neon via Vercel Marketplace

Create, view, edit and delete students/courses. Enroll students, display joined names, change enrollment status and remove relationships. Enforce validation, uniqueness and foreign keys. Show loading, empty, failure and success states. Test and document the result.

Vercel is the sole application deployment platform. Neon operates the database as a third-party Marketplace provider. The frontend never connects directly to PostgreSQL. Two Vercel projects use this repository: root backend for FastAPI and root frontend for Next.js.

How to use this course

Intended learning outcomes

Design a relational schema, write useful SQL, build and test a persistent Python API, create typed React forms with Next.js, connect the two applications over HTTP and deploy both on Vercel. Explain a real request end to end and reproduce the setup on another computer.

You should already understand Python variables, collections, functions, modules, classes and exceptions. No SQL, frontend language, Tailwind, React or deployment knowledge is assumed. The first lesson includes a Python diagnostic. Review functions and dictionaries if those are still difficult.

This course builds a substantial foundation. Expertise requires repeated independent projects, security, testing, performance work and operating systems in practice. Do not treat completion of copied code as professional mastery.

Learning sequence

First learn SQL and data modeling. Next connect Python to PostgreSQL, build and test FastAPI, and deploy a complete working backend. Only after that checkpoint begin TypeScript fundamentals. Then learn React and Next.js, connect the existing API, verify the complete workflow and deploy the frontend. See CONTENTS for all 48 lessons.

Each lesson includes vocabulary, conceptual explanation, exact procedures, complete file content where code is introduced, expected results, exercises, answers and tutor/self-study guidance. Later lessons may replace a whole earlier file: commit working code before replacing it. Do not paste a fragment into a location the lesson did not specify.

Keep reference and practice separate

Clone this repository into a folder named course-reference. Create a sibling folder student-project for the files you type. Both folders should be visible in your editor or file manager. Paths such as backend/main.py in a lesson are relative to student-project. Terminal commands explicitly name their working folder.

The finished backend and frontend in course-reference let a tutor rehearse the end result. They are also useful for comparison, but learners should follow the sequential notes and explain each stage.

Recovery checkpoints

From course-reference run python scripts/checkpoint.py 18 ../checkpoint-18 (use python3 or py -3.12 if appropriate before activating a virtual environment). This creates a NEW practice folder with the working code through Lesson 18. It refuses to overwrite any existing destination. Use a different destination each time.

Available source checkpoints: 15, 16, 18, 20, 22, 24, 33, 34, 35, 38, 41, 42, 44, 46, 47 and 48. No checkpoint contains credentials, installed packages or database records. Follow SETUP to create .env files, install dependencies and initialize an appropriately fresh DEVELOPMENT database. Intermediate checkpoints may intentionally lack later routes.

Compare your work with the checkpoint one file at a time. Fix the cause, explain the difference and repeat the test. A successful comparison is a learning aid, not a substitute for understanding.

Completion gates

Pass the SQL foundations and relational-query assessments before the API stage. Pass the backend CRUD/testing/deployment gate before frontend work. Pass TypeScript foundations before typed React. Finish local integration before production frontend deployment. The assessment guide gives tasks, expected evidence, marking and remediation.

For each lesson, predict the result, perform the action, inspect the evidence, reproduce it without copying and commit the working change. Keep a debugging journal with expected/actual results and fixes. Pair learners should alternate roles, but each must independently explain code and make a small change.

Scope and progression

Core scope: Student/Course/Enrollment management, relational constraints, SQL joins/reports, SQLAlchemy, Pydantic, FastAPI, TypeScript basics, React props/state/forms/effects, Tailwind styling, Next.js App Router, HTTP integration, CORS, tests, environment variables, Vercel deployments and a reproducible handover.

The classroom UI displays up to 100 records per list. The API supports limit/offset; UI pagination is a further task. The demo has no login or authorization and must contain only fictional data. Authentication, role-based permissions, payments, uploads, WebSockets, advanced caching and background jobs are not silently claimed as finished features.

For further professional practice:

  1. Add server-enforced authentication and role permissions, with denied-access tests.
  2. Introduce Alembic migrations, backup/restore rehearsal and deployment-compatible schema changes.
  3. Add pagination/search, query plans and measured indexes on larger datasets.
  4. Add browser regression automation, protected secrets and CI deployment gates.
  5. Add monitoring, structured logs, recovery procedures and an operational owner.
  6. Build a second domain independently, such as inventory or library loans, with its own business rules and tests.

All application deployments remain on Vercel. PostgreSQL remains an external Marketplace database. Add complexity only when you can explain the preceding implementation.

Lesson 01 From Python data to relational tables

Start here · Next lesson

Learning objectives

Explain database, table, row and column; identify a primary key; connect to a development PostgreSQL database.

Before you begin

Pass the preceding lesson's result check. Keep your files in student-project and these notes in course-reference. Complete only the setup sections directed by this lesson. Commit working code before replacing a complete file. A recovery checkpoint creates code in a new folder; it does not copy credentials or initialize database data.

Vocabulary

Database: organized persistent data. Table: records with a common structure. Row: one record. Column: one attribute. Primary key: unique row identifier.

Explanation

A Python list disappears when a process ends unless you save it. A database persists independently of the program and can enforce rules when several programs use the same data. A student is one entity; a course is another. Do not store course names as a comma-separated string on the student: we will model their relationship explicitly.

Read this Python record: {"full_name": "Amina Demo", "email": "amina@example.com"}. In a table, full_name and email become named columns. Each row also receives an id. IDs identify records; a person's name does not, because two people can have the same name.

Worked procedure

  1. Complete SETUP A–D. Open only the development database SQL editor. Confirm its branch/database name before every write.
  2. On paper, draw three sample student rows with id, full_name and email. Choose appropriate text lengths. Explain why email must be unique in our application.
  3. In the SQL editor run the query below. It reads system information and creates nothing.
  4. Predict whether two students may share a name, an email, or an id. Discuss the business rules before writing SQL.
  5. Save a learning journal entry explaining database vs Python list. Do not put credentials in it.
SELECT current_database(), current_user, version();

Check your result

One row identifies the database and user; the version contains PostgreSQL. Each drawn student has a different id.

If the result differs, read the first error, confirm your terminal directory and environment, save the file and compare it with this complete example. Consult troubleshooting. Use an appropriately fresh development database when exact seed results are required; never reset valuable data to match a screenshot.

Independent practice

List three entities in a library system. Give each a key and two attributes. Diagnostic: write a Python function that returns the emails in a list of dictionaries.

Answer and reasoning

Try the task first. Library examples: books(id, title, isbn), members(id, name, email), loans(id, book_id, member_id). A possible diagnostic is def emails(students): return [s["email"] for s in students]. If dictionary access is unfamiliar, review it before Lesson 13.

Have each learner explain one decision and diagnose one deliberate mistake. Give support by reducing sample data rather than skipping the concept; use the independent task for further practice.

Lesson 02 Choose data types and translate business rules

Previous lesson · Next lesson

Learning objectives

Choose PostgreSQL types; distinguish null from blank values; turn requirements into constraints.

Before you begin

Pass the preceding lesson's result check. Keep your files in student-project and these notes in course-reference. Complete only the setup sections directed by this lesson. Commit working code before replacing a complete file. A recovery checkpoint creates code in a new folder; it does not copy credentials or initialize database data.

Vocabulary

Text: characters. Integer: whole number. Numeric: exact decimal. Boolean: true/false. Date: calendar value. NULL: missing or unknown value.

Explanation

Choose a type from the meaning of a value, not only its appearance. A phone number is text because it may include + and leading zeros and is not added mathematically. Credits is an integer because fractional credits are outside this application's rules. Money should use an appropriate exact numeric representation rather than floating point.

NULL differs from an empty string and from zero. A required name should be NOT NULL and nonblank. SQL treats unknown values differently from ordinary values; predicates may evaluate to unknown. Use IS NULL to find missing values.

Requirements should become explicit rules: a student's email is unique, a course code is unique, credits are in the range 1–6, and enrollment refers to existing parents. Record these rules before creating tables. They guide SQL, API validation, UI feedback and tests.

Worked procedure

  1. Run the read-only expressions below in the development SQL editor. No tables are required yet.
  2. Predict each result and identify its PostgreSQL type. Explain why a phone number should not be cast to integer.
  3. Write a data dictionary with field, meaning, type, required status and uniqueness for our three entities.
  4. Compare the dictionary with the next lesson's schema only after completing your own attempt.
SELECT 'Amina'::text AS name, 3::integer AS credits, true AS active;
SELECT NULL IS NULL AS missing, '' = '' AS blank, 0 = 0 AS zero_value;
SELECT '2026-01-01'::date AS example_date;

Check your result

All statements return one row. Missing, blank and zero are different concepts, even when their simple checks each return true.

If the result differs, read the first error, confirm your terminal directory and environment, save the file and compare it with this complete example. Consult troubleshooting. Use an appropriately fresh development database when exact seed results are required; never reset valuable data to match a screenshot.

Independent practice

Choose types for invoice amount, course title, registration number and enrollment date. State one rule for each.

Answer and reasoning

Try the task first. Use numeric for an exact amount, text/varchar for a title and registration number, and date for enrollment date. A registration number is an identifier, so preserve leading zeros and add a uniqueness rule where required.

CREATE TABLE students (

A Session tracks pending ORM changes and transaction state. add queues an object; commit flushes the SQL and commits it. refresh retrieves database-generated fields. If the database rejects the write, rollback is required to clear the failed transaction.

The Session dependency closes its session after each request. The engine may live across requests, but a Session object must not. Good request isolation and database constraints remain necessary under concurrent traffic.

type ValidationIssue = {loc:(string | number)[]; msg:string};
type ApiError = {detail?:string | ValidationIssue[]};
const base = process.env.NEXT_PUBLIC_API_BASE_URL;
export async function api<T = void>(path:string, options:RequestInit = {}):Promise<T> {
  if (!base) throw new Error('Set NEXT_PUBLIC_API_BASE_URL and restart or rebuild the frontend.');
  const response = await fetch(`${base.replace(/\/$/, '')}${path}`, {
    ...options,
    headers: { ...(options.body ? { 'Content-Type': 'application/json' } : {}), ...options.headers },
    cache: 'no-store',
  });
  if (!response.ok) {
    const body:ApiError = await response.json().catch(() => ({}));
    const detail = Array.isArray(body.detail)
      ? body.detail.map(item => `${item.loc.join('.')}: ${item.msg}`).join('; ')
      : body.detail;
    throw new Error(detail || `Request failed (${response.status})`);
  }
  if (response.status === 204) return undefined as T;
  return response.json() as Promise<T>;
}

Data design and API contract

Relational model

students                       enrollments                         courses
id PK                  ┌────── student_id FK          ┌────────── id PK
full_name              │       course_id FK ──────────┘           code UNIQUE
email UNIQUE           │       id PK                              title
  id ──────────────────┘       enrolled_on                         credits
                               status
                               UNIQUE(student_id, course_id)

Each student and course can have many enrollments. Enrollment is the relationship record. IDs are generated by PostgreSQL; clients must not supply an id on create. All columns in the initial schema are NOT NULL.

Table Field Type and rule
students id integer generated primary key
students full_name varchar 100, nonblank
students email varchar 254, unique; API validates address and lowercases it
courses id integer generated primary key
courses code varchar 20, unique, nonblank; API uppercases it
courses title varchar 120, nonblank
courses credits integer from 1 to 6
enrollments id integer generated primary key
enrollments student_id foreign key to students.id, indexed
enrollments course_id foreign key to courses.id, indexed
enrollments enrolled_on date, database default CURRENT_DATE
enrollments status active, completed or withdrawn; default active

A student/course pair may exist once. Deleting a referenced parent is restricted. Delete the enrollment explicitly before deleting a student or course. Withdrawal keeps history; deletion removes the relationship. Do not silently cascade parent deletes.

Boundary between SQL models and API schemas

Handwritten SQL creates the actual PostgreSQL tables. SQLAlchemy models map those existing tables to Python. Pydantic schemas validate requests and serialize responses. They have different responsibilities. Editing a Python model does NOT migrate an existing table. The initial application never calls create_all on startup. A later schema change needs a reviewed incremental migration.

Python string lengths and API fields mirror SQL lengths. Database-generated values are refreshed after commit. Validation failures occur before the route handler (422). Database conflicts are caught at commit and rolled back (409). Missing resources use 404. SQLAlchemy parameter binding and ORM statements keep data separate from query structure.

The schema itself enforces nonblank names, unique emails/codes, valid credits/statuses and foreign keys. Email syntax and uppercase/lowercase normalization are API policies; a direct SQL writer must follow those policies too. For stronger database-wide case-insensitive uniqueness, teach a later migration using a lower(email) index or an appropriate PostgreSQL type, with duplicate cleanup first.

Exact JSON examples

StudentWrite: {"full_name":"Amina Demo","email":"amina@example.com"}.

StudentRead: {"id":1,"full_name":"Amina Demo","email":"amina@example.com"}.

CourseWrite: {"code":"SQL101","title":"Relational databases","credits":3}.

CourseRead adds "id":1. Credits must be a JSON integer, not a string or fraction.

EnrollmentWrite: {"student_id":1,"course_id":1}. Use actual returned IDs; never assume seed IDs are exactly 1.

EnrollmentUpdate: {"status":"completed"}. It cannot move an enrollment to another student/course. Delete and recreate the relationship for that operation.

EnrollmentRead: {"id":1,"student_id":1,"course_id":1,"enrolled_on":"2026-01-01","status":"active"}. The sample date is illustrative; the real database supplies its current date.

EnrollmentDetail is returned by the LIST endpoint and adds student_name, course_code and course_title. The detail GET returns EnrollmentRead. There is no nested ORM relationship serialization; the list route performs an explicit SQL join.

Failure contract

422 means invalid body/path/query shape or invalid field values. Duplicate email, duplicate code, duplicate enrollment or a restricted parent delete returns 409 with {"detail":"Conflict with an existing record or relationship"}. Missing records, including missing parents during enrollment creation, return 404 with {"detail":"Record not found"}. Unexpected database outages are server failures to diagnose in logs, not automatically duplicate conflicts.

The frontend displays validation details or a readable fallback. It must not parse JSON after a 204. Errors should not return SQL, passwords or stack traces to the browser. The current app does not implement login, access control, total counts, server-side search or pagination controls in the UI. Those are explicit extensions, not hidden finished features.

Tailwind styling from setup to usable components

What Tailwind does

Tailwind turns the utility classes used in your source into the styles a browser needs. In TSX write className, not class. This course uses utility classes for spacing, color, typography, layout, responsive behavior and interactive states. You do not create custom selector rules.

The required app/globals.css file contains only @import "tailwindcss";. This loads Tailwind into the build. The root layout imports that entry once. Keeping the filename does not mean the course has switched back to custom CSS.

Installation procedure

For the reference or a generated checkpoint, copy package.json, package-lock.json, postcss.config.mjs, tsconfig.json and next-env.d.ts; run npm ci inside frontend. Create the app files from Lesson 33. For a new Next.js scaffold choose TypeScript and Tailwind Yes.

If adding Tailwind manually to an existing Next.js app, run:

npm install -D tailwindcss @tailwindcss/postcss postcss

Create frontend/postcss.config.mjs with the complete configuration:

export default {plugins: {'@tailwindcss/postcss': {}}};

This standard build configuration is a module for PostCSS; application components remain TypeScript. Create frontend/app/globals.css with only:

Ensure app/layout.tsx contains import './globals.css';. Restart npm run dev. For the supplied locked repository use npm ci rather than changing versions. See official installation.

Buttons and pending states

A button needs a meaningful text label, a type appropriate to its form behavior and visible keyboard focus. Disable repeated submission while busy. Tailwind's disabled variant changes presentation; the disabled HTML property is what actually disables the button.

<button type="submit" disabled={busy}
  className="rounded-md bg-sky-900 px-4 py-2 font-medium text-white hover:bg-sky-800 focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-amber-600 disabled:cursor-wait disabled:opacity-50">
  {busy ? 'Saving…' : 'Save'}
</button>

This is a component fragment, not a complete file: busy is the boolean state supplied by the complete form component in the lesson. For a cancel button use type="button". State variants.

Tables and narrow screens

Wrap tables in a div with overflow-x-auto. Keep real table/caption/th semantics. Give header cells scope="col" and readable padding. Do not shrink text until the whole table becomes unreadable; let the table scroll in its container.

The reference app uses utility classes directly on its table, caption, headings and cells. Its layout uses a max-width content area with responsive horizontal padding. Test near 375px and on a wider screen; also test keyboard focus and long course titles.

Keep class names detectable

Use complete class strings. active ? 'bg-emerald-100' : 'bg-slate-100' exposes both class names to the build scanner. Constructing bg-${color}-100 from arbitrary data may produce no matching utility in the generated output. Prefer an explicit mapping of permitted variants.

The navigation's bracketed classes such as [&_a]:py-2 apply utilities to descendant links. This is an optional Tailwind variant convenience; the same utilities can be written directly on each Link. Explain the simpler direct classes before discussing the shared variant syntax.

Common failures

If all styling is missing, check the Tailwind packages, postcss.config.mjs, the single Tailwind entry import and the layout's import. Restart the dev server and inspect build errors. If only one class is missing, check spelling and whether it was constructed dynamically. If a heading looks like body text, add explicit text and weight utilities: Tailwind's base reset removes some browser defaults.

If a control cannot be used with a keyboard, adding color classes is not a fix. Check its semantic element, label, disabled state and event behavior. If a table overflows, inspect its wrapper. If an error is communicated only by red color, add meaningful text and role="alert".

Practice and answer

Create a panel with a title, explanatory paragraph and two actions. Make padding larger at sm:, keep the base layout usable on a phone and give both actions visible focus. Explain every class. The backend uses SQLAlchemy 2-style mappings and Pydantic 2 directly. FastAPI's introductory database tutorial uses SQLModel, but it does not require that ORM. The backend uses normal def routes with synchronous psycopg/SQLAlchemy and one session per request. NullPool plus a provider-pooled URL is a small-serverless-workload teaching design. The frontend uses strict TypeScript and TSX, with type definitions for API records, props, form events and state. TypeScript describes expected shapes at compile time; the API remains responsible for runtime request/response validation. The complete app uses no any-based state shortcuts.

The course uses two Vercel application projects, not another application host. Neon is the database operator.
