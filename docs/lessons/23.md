# Lesson 23 Test isolation and backend deployment readiness

## Learning objectives

Use disposable test data; distinguish regression checks from production smoke tests; prepare reproducible dependencies.

## Before you begin

Pass the preceding lesson's result check. Keep your files in student-project and these notes in course-reference. Complete only the setup sections directed by this lesson. Commit working code before replacing a complete file. A recovery checkpoint creates code in a new folder; it does not copy credentials or initialize database data.

## Vocabulary

Fixture isolation: each test has controlled state. Lockfile: exact resolved dependencies. Smoke test: critical deployed behavior checked briefly.

## Explanation

Tests must be repeatable without damaging valuable data. The local fallback creates a disposable in-memory database. The PostgreSQL path requires both a test URL and an explicit reset flag because it recreates the course tables. Treat the flag as a deliberate destructive action limited to an already-disposable database.

The PostgreSQL test path applies 001_schema.sql, so API behavior is checked against the same handwritten structure as deployment. The workflow also runs seed and practice SQL to catch syntax errors. A workflow file existing in Git does not mean its run succeeded; inspect the job result.

requirements.txt pins runtime packages and requirements-dev.txt adds test tools. Production deployments should not install the document rendering tools or a local-only development environment.

## Worked procedure

1. Run the local tests from backend using the complete command below.
2. Follow TESTING.md to use a disposable PostgreSQL test database. Verify the target before enabling resets.
3. Read the CI workflow and identify which credentials are ephemeral test-only values, which service is PostgreSQL and which job builds the frontend later.
4. Prepare the backend deployment checklist: required tracked files, ignored secrets, initialized production schema and the expected health/docs URLs.

```sh
python -m pip check
python -m pytest -q
```

## Check your result

Package checks and API regression tests pass. PostgreSQL test evidence names the disposable target without exposing its credentials.

If the result differs, read the first error, confirm your terminal directory and environment, save the file and compare it with this complete example. Consult [troubleshooting](../TROUBLESHOOTING.md). Use an appropriately fresh development database when exact seed results are required; never reset valuable data to match a screenshot.

## Independent practice

Why is a passing /health endpoint insufficient evidence for database CRUD deployment?

## Answer and reasoning

Try the task first. /health performs no database query. Only real read/write requests and persistence checks establish that configuration, schema and database access work together.

## Tutor guidance and self study review

Ask the learner to predict the result before running each step. Demonstrate the worked procedure, then let the learner reproduce it independently. Use the result check as the completion gate. Have each learner explain one decision and diagnose one deliberate mistake. Give support by reducing sample data rather than skipping the concept; use the independent task for further practice.

For self study, close the example and repeat the key action from memory. Reopen it to compare, record the error and fix, then commit the working result. Do not advance simply because code was copied successfully: explain what it does and why the check proves it.
