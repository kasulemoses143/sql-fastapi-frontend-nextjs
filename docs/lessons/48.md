# Lesson 48 Demonstrate the capstone and plan independent work

[Previous lesson](47.md) · [Independent projects](../START-HERE.md#scope-and-progression)

## Learning objectives

Demonstrate an end-to-end workflow; explain the architecture independently; diagnose one failure and identify next learning goals.

## Before you begin

Pass the preceding lesson's result check. Keep your files in student-project and these notes in course-reference. Complete only the setup sections directed by this lesson. Commit working code before replacing a complete file. A recovery checkpoint creates code in a new folder; it does not copy credentials or initialize database data.

## Vocabulary

Capstone: integrated final project. Evidence: observable results supporting a claim. Reflection: explain what you understand and what needs further practice.

## Explanation

Your final explanation should follow a real action: a form holds state; submission creates JSON; the browser sends HTTP; FastAPI validates it; a session executes SQL; PostgreSQL enforces constraints; the response updates the page. Explain each boundary in your own words.

Professional development continues beyond a working classroom app. Authentication, authorization, data privacy, migrations, monitoring, recovery, performance and maintainability are follow-on learning goals. Do not describe the unauthenticated demo as suitable for real student records.

## Worked procedure

1. Present a complete demonstration: create a student/course, enroll, update status, refresh, provoke a duplicate conflict, remove the enrollment and delete the unreferenced parent.
2. Show the ERD, one SQL join and one passing test. Give the source commit and both Vercel URLs.
3. Individually explain one teacher-selected route and one React event handler, then make a small requested change.
4. Complete the final rubric and reflect on three problems you diagnosed and how you verified each fix.
5. Choose the next project from START-HERE.md. Keep a deployment and debugging journal as you work independently.



## Check your result

All required features are deployed and demonstrable, and each student can explain and modify the system independently.

If the result differs, read the first error, confirm your terminal directory and environment, save the file and compare it with this complete example. Consult [troubleshooting](../TROUBLESHOOTING.md). Use an appropriately fresh development database when exact seed results are required; never reset valuable data to match a screenshot.

## Independent practice

Choose one advanced feature and write an acceptance test in plain language before implementing it.

## Answer and reasoning

Try the task first. For authorization: “A user without the registrar role cannot create or delete a student, even by calling the API directly.” The requirement must be enforced server-side and tested with both allowed and denied cases.

## Tutor guidance and self study review

Ask the learner to predict the result before running each step. Demonstrate the worked procedure, then let the learner reproduce it independently. Use the result check as the completion gate. Have each learner explain one decision and diagnose one deliberate mistake. Give support by reducing sample data rather than skipping the concept; use the independent task for further practice.

For self study, close the example and repeat the key action from memory. Reopen it to compare, record the error and fix, then commit the working result. Do not advance simply because code was copied successfully: explain what it does and why the check proves it.
