# Lesson 21 Organize the API and document its contract

[Previous lesson](20.md) · [Next lesson](22.md)

## Learning objectives

Explain module responsibilities; document each route; avoid unnecessary abstraction while learning.

## Before you begin

Pass the preceding lesson's result check. Keep your files in student-project and these notes in course-reference. Complete only the setup sections directed by this lesson. Commit working code before replacing a complete file. A recovery checkpoint creates code in a new folder; it does not copy credentials or initialize database data.

## Vocabulary

Contract: agreed request/response behavior. Module boundary: where a responsibility lives. Refactor: reorganize code while preserving behavior.

## Explanation

The project keeps db.py for connection/session setup, models.py for relational mapping, schemas.py for API validation and main.py for route behavior/CORS. This makes it possible to find the source of a failure without a large framework hierarchy.

A useful API contract specifies method, path, body, response and error behavior. “CRUD works” is too vague: PUT requires all editable fields, DELETE has no body, and enrollment's list response adds joined labels. Frontend code must follow these details.

APIRouter can later split routes into resource modules. Introduce it only when students can explain the existing route functions. Refactoring should run the same regression suite before and after, not add behavior accidentally.

## Worked procedure

1. Read API-CONTRACT.md, especially the endpoint and failure tables.
2. In /docs compare the currently available student/course routes with the contract. Enrollment routes are added next.
3. Trace one student POST through the four files and draw the dependency arrows.
4. Write your own contract entry for PUT /courses/{id}, including required body and 404/409/422 outcomes. No application changes are required.

```json
{"code":"API101","title":"Python web APIs","credits":3}
```

## Check your result

Your contract entry matches the implemented route, and you can name the responsible module for each step.

If the result differs, read the first error, confirm your terminal directory and environment, save the file and compare it with this complete example. Consult [troubleshooting](../TROUBLESHOOTING.md). Use an appropriately fresh development database when exact seed results are required; never reset valuable data to match a screenshot.

## Independent practice

Where would you change a course title maximum length? Is changing only the frontend enough?

## Answer and reasoning

Try the task first. Update the schema policy and SQLAlchemy mapping, apply a deliberate database migration if the database length changes, and update the form. Recheck tests and documentation. A frontend-only change cannot redefine the server/database contract.

## Tutor guidance and self study review

Ask the learner to predict the result before running each step. Demonstrate the worked procedure, then let the learner reproduce it independently. Use the result check as the completion gate. Have each learner explain one decision and diagnose one deliberate mistake. Give support by reducing sample data rather than skipping the concept; use the independent task for further practice.

For self study, close the example and repeat the key action from memory. Reopen it to compare, record the error and fix, then commit the working result. Do not advance simply because code was copied successfully: explain what it does and why the check proves it.
