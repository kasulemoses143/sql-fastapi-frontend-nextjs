## Vocabulary

Generic type argument: caller-selected expected type. Pagination: fetch a bounded result window. Contract drift: server and client shapes disagree.

## Explanation

api<Student[]> tells TypeScript what a successful response is expected to contain. It does not inspect the JSON. Our FastAPI response models enforce the server-side shape; clients for less-trusted services should add runtime response parsing. A type assertion is not a validator.

The API supports limit and offset while the core classroom UI displays at most 100 rows. This is an explicit limit. Displaying the first page as though it were the entire database would be misleading for a larger application. Real pagination needs next/previous controls, a stable sort and an appropriate end-of-list or total-count strategy.

GET requests are safe to repeat; POST requests may create duplicates if blindly retried. The helper does not automatically retry writes. After an ambiguous network failure, check saved state before submitting again.

## Worked procedure

1. With the API running, open /docs GET /students and try limit=1, offset=0, then offset=1.
2. Compare actual IDs in the responses. An offset counts rows, not ID values.
3. Read the bounded API helper call below as a type/contract example. The core UI still uses its default window.
4. As an extension, sketch next/previous controls with loading/empty/error states before writing them. Do not claim pagination controls are implemented in the core app.

## Independent practice

Why should page ordering include a stable unique key? What changes if rows are added between offset requests?

## Answer and reasoning

Try the task first. Stable ordering avoids arbitrary page boundaries. Concurrent inserts/deletes can still shift offsets; keyset pagination is often better for changing large datasets. It is a deliberate later extension.
