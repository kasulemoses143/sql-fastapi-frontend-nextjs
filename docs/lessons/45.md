# Lesson 45 Responsive usability security and release review

## Learning objectives

Check the integrated app on small screens; understand authentication vs CORS; prepare release evidence.

## Before you begin

Pass the preceding lesson's result check. Keep your files in student-project and these notes in course-reference. Complete only the setup sections directed by this lesson. Commit working code before replacing a complete file. A recovery checkpoint creates code in a new folder; it does not copy credentials or initialize database data.

## Vocabulary

Authentication: identify the caller. Authorization: decide permitted actions. CORS: browser response access policy. Least privilege: only necessary access.

## Explanation

CORS is not login and does not stop a command-line client from calling an unauthenticated API. This demo must use fictional data. Before real school use, add identity, server-side role checks, auditability, privacy controls, backup/recovery and an operational owner.

Never store secrets in frontend code, browser local storage as a substitute for secure architecture, or NEXT_PUBLIC variables. The database URL belongs exclusively to the backend environment. Rotate any exposed credentials immediately; removing a visible file is not enough.

Usability review should include narrow screens, keyboard navigation, names that repeat, long titles and readable errors. The data model uses unique IDs even when labels match. A larger deployment should make selection labels sufficiently informative without exposing unnecessary personal information.

## Worked procedure

1. Run the complete local workflow, then narrow the browser to approximately 375px width. Verify readable forms and horizontally scrollable tables.
2. Use keyboard-only navigation to add and edit a record. Check label, focus, pending state, error and success feedback.
3. Search tracked source for real credentials and confirm .env files are ignored. Review variable names in DEPLOYMENT.md.
4. Write a release checklist covering source commit, database target, both Vercel projects, CORS, tests, rollback limits and remaining limitations.

```sh
git status --short
git ls-files
```

Inspect the tracked filenames. Real .env and .env.local files must not be listed.

## Check your result

The integrated app is usable with keyboard and narrow screens, and the release checklist contains no secret values.

If the result differs, read the first error, confirm your terminal directory and environment, save the file and compare it with this complete example. Consult [troubleshooting](../TROUBLESHOOTING.md). Use an appropriately fresh development database when exact seed results are required; never reset valuable data to match a screenshot.

## Independent practice

A caller uses curl to POST a student from an unapproved origin. Does CORS guarantee rejection? What would enforce access?

## Answer and reasoning

Try the task first. No. CORS is enforced by browsers and is not an API authorization system. Server authentication and authorization must enforce access rules for every caller.

## Tutor guidance and self study review

Ask the learner to predict the result before running each step. Demonstrate the worked procedure, then let the learner reproduce it independently. Use the result check as the completion gate. Have each learner explain one decision and diagnose one deliberate mistake. Give support by reducing sample data rather than skipping the concept; use the independent task for further practice.

For self study, close the example and repeat the key action from memory. Reopen it to compare, record the error and fix, then commit the working result. Do not advance simply because code was copied successfully: explain what it does and why the check proves it.
