## Learning objectives

Design the capstone ERD independently; apply constraints to a new case; explain parameterized queries before Python integration.

## Before you begin

Pass the preceding lesson's result check. Keep your files in student-project and these notes in course-reference. Complete only the setup sections directed by this lesson. Commit working code before replacing a complete file. A recovery checkpoint creates code in a new folder; it does not copy credentials or initialize database data.

## Vocabulary

ERD: entity relationship diagram. Normalization: organize facts to avoid inconsistent duplication. Parameter: a separate data value bound to a query.

## Explanation

Store a student's email once in students, not once per enrollment. Store course title once in courses. If a title changes, one row changes instead of many inconsistent copies. Enrollment status belongs to the relationship, not to either parent.

Input is data, not SQL syntax. A query built with string interpolation can turn user input into executable SQL. In Lesson 13 we bind the value separately using SQLAlchemy's named parameter syntax. Do not “sanitize” input by removing quotes and then concatenate it.

## Worked procedure

1. Without opening the reference schema, draw Student, Course and Enrollment with types, primary keys, foreign keys and unique rules.
2. Swap diagrams with a partner. Ask what happens when a referenced course is deleted and when a duplicate enrollment is inserted.
3. Write three SQL queries: students ordered by name, enrollment labels with a join, counts including empty courses.
4. Discuss how a user-supplied email should enter a query. Compare `... WHERE email = :email` plus a parameter dictionary with an f-string.
5. Complete the remaining relational SQL assessment. Retake any failed key/relationship task before beginning API work.

## Independent practice

Adapt the model to books, members and loans. Where should due_date live? Can a member borrow a book twice at different times?

## Answer and reasoning

Try the task first. due_date belongs on loans. Unlike our one-enrollment-per-pair rule, historical loans may permit repeated member/book pairs, so a permanent unique pair would be wrong. Schema rules depend on the domain, not on memorized templates.

## Tutor guidance and self study review

Ask the learner to predict the result before running each step. Demonstrate the worked procedure, then let the learner reproduce it independently. Use the result check as the completion gate. Have each learner explain one decision and diagnose one deliberate mistake. Give support by reducing sample data rather than skipping the concept; use the independent task for further practice.

For self study, close the example and repeat the key action from memory. Reopen it to compare, record the error and fix, then commit the working result. Do not advance simply because code was copied successfully: explain what it does and why the check proves it.
