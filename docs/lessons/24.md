# Lesson 24 Deploy and assess the working backend

[Previous lesson](23.md) · [Next lesson](25.md)

## Learning objectives

Deploy FastAPI on Vercel; use separate production configuration; verify persistent CRUD over HTTPS.

## Before you begin

Pass the preceding lesson's result check. Keep your files in student-project and these notes in course-reference. Complete only the setup sections directed by this lesson. Commit working code before replacing a complete file. A recovery checkpoint creates code in a new folder; it does not copy credentials or initialize database data.

## Vocabulary

Deployment: running a released version remotely. Build: prepare dependencies and code. Production: intended released environment. Log: recorded server events.

## Explanation

Deployment moves the Python application into Vercel's managed runtime. It does not copy your local .env file, and a successful build does not prove the database is configured. The backend needs its own environment variables in each intended environment.

A serverless process may restart or scale. Lists, dictionaries and files in that process are not our permanent database. PostgreSQL stores the records. Do not run schema creation or seed insertion on every request or cold start.

The backend phase ends here. Students demonstrate SQL, API requests and deployment using /docs; no TypeScript, React or frontend UI is required yet.

## Worked procedure

1. Follow DEPLOYMENT.md sections A–C, including the separate production database and one-time schema/seed steps.
2. Push your backend files to your own GitHub repository. Import with Vercel project root backend and the FastAPI preset/detection.
3. Set production variables, deploy and record the stable production API URL. Visit /health and /docs over HTTPS.
4. Perform the backend demonstration and deployed smoke checklist. Confirm a newly created row survives another request after the first process is idle.
5. Save the commit SHA, production API URL and test evidence. Fix deployment failures before The frontend phase begins.



## Check your result

A public or appropriately accessible HTTPS API supports real CRUD with persistent PostgreSQL data. There is no frontend deliverable this stage.

If the result differs, read the first error, confirm your terminal directory and environment, save the file and compare it with this complete example. Consult [troubleshooting](../TROUBLESHOOTING.md). Use an appropriately fresh development database when exact seed results are required; never reset valuable data to match a screenshot.

## Independent practice

Explain why a working local API can return 500 on Vercel. Find which log and configuration you would check first.

## Answer and reasoning

Try the task first. Possible causes include missing DATABASE_URL, wrong project root, missing runtime dependency, an unapplied production schema or incorrect provider TLS/credentials. Read build/runtime logs, then check configuration names and target environment without exposing secrets.

## Tutor guidance and self study review

Ask the learner to predict the result before running each step. Demonstrate the worked procedure, then let the learner reproduce it independently. Use the result check as the completion gate. Have each learner explain one decision and diagnose one deliberate mistake. Give support by reducing sample data rather than skipping the concept; use the independent task for further practice.

For self study, close the example and repeat the key action from memory. Reopen it to compare, record the error and fix, then commit the working result. Do not advance simply because code was copied successfully: explain what it does and why the check proves it.
