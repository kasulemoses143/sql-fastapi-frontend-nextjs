# Lesson 06 Transactions safe writes and database errors

## Learning objectives

Use rollback for safe experiments; inspect affected rows with RETURNING; diagnose constraint errors.

## Vocabulary

RETURNING: retrieve changed records. Atomicity: all intended changes succeed together. Isolation: control how transactions observe concurrent work.

## Explanation

A transaction groups work. If you insert a student and then fail to enroll them, a transaction can undo the student's insertion when those actions are one business operation. That is different from a sequence of unrelated committed requests.

RETURNING shows exactly which rows a write affected. Start with a SELECT using the intended WHERE clause, then use the same condition for UPDATE/DELETE. Never leave a transaction open while you stop to work on another task: it can hold locks and make other users wait.

Constraint errors are meaningful evidence. Read the first rejected rule, roll back, and correct the cause. Do not remove a foreign key merely to make an invalid write succeed.

## Worked procedure

1. Inspect Brian with SELECT. Run the complete transaction below; read the changed row before rollback.
2. Query Brian again and confirm the original name is restored.
3. Begin another transaction and attempt a duplicate email. Observe the error, then issue ROLLBACK explicitly.
4. Describe what COMMIT would have changed in the first exercise. Keep your practice writes isolated from valuable data.

```sql
SELECT id, full_name FROM students WHERE email='brian@example.com';
BEGIN;
UPDATE students SET full_name='Brian Changed' WHERE email='brian@example.com' RETURNING id, full_name;
ROLLBACK;
SELECT id, full_name FROM students WHERE email='brian@example.com';
```

## Check your result

The update returns Brian Changed inside the transaction; the later SELECT returns Brian Demo.

If the result differs, read the first error, confirm your terminal directory and environment, save the file and compare it with this complete example. Consult [troubleshooting](../TROUBLESHOOTING.md). Use an appropriately fresh development database when exact seed results are required; never reset valuable data to match a screenshot.

## Independent practice

Explain why wrapping DELETE without WHERE in a transaction is still risky. What should you inspect before committing?

## Answer and reasoning

Try the task first. An accidental COMMIT still makes the deletion permanent. First verify a precise WHERE clause and the affected rows; use RETURNING and a backup/restore policy for important data.

Have each learner explain one decision and diagnose one deliberate mistake. Give support by reducing sample data rather than skipping the concept; use the independent task for further practice.
