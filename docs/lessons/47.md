# Lesson 47 Test debug and prepare a handover

[Previous lesson](46.md) · [Next lesson](48.md)

## Learning objectives

Run regression checks; verify accessibility and failure behavior; write a reproducible project README.

## Before you begin

Pass the preceding lesson's result check. Keep your files in student-project and these notes in course-reference. Complete only the setup sections directed by this lesson. Commit working code before replacing a complete file. A recovery checkpoint creates code in a new folder; it does not copy credentials or initialize database data.

## Vocabulary

Smoke test: quick critical workflow check. Regression suite: repeated behavioral checks. Handover: enough information for another person to run and support the project.

## Explanation

A demo that worked once is not the same as a reproducible system. Re-run the database and API tests, build the frontend and test the deployed workflow after the final code change. A build passing does not prove the deployed API URL or database credentials are correct.

Check keyboard navigation, visible focus, meaningful labels, readable errors and a small-screen table. A green success notice alone is insufficient: inspect the saved row after refresh. Record limitations honestly, including the absence of authentication and the small classroom dataset.

## Worked procedure

1. Run the commands in TESTING.md using a disposable PostgreSQL database; then run npm ci and npm run build in frontend.
2. Perform the manual matrix against the deployed application, including duplicate, invalid input, referenced deletion, empty list and API outage cases.
3. Navigate all forms using only the keyboard. At approximately 375px browser width confirm content is readable and tables can scroll.
4. Write your own README with purpose, ERD, prerequisites, exact startup commands, variable names, database setup, URLs, tests and limitations.
5. Swap README instructions with a partner who has not set up your project. Record and fix every missing step.



## Check your result

Another learner can follow the README, and final regression/manual checks have dated evidence.

If the result differs, read the first error, confirm your terminal directory and environment, save the file and compare it with this complete example. Consult [troubleshooting](../TROUBLESHOOTING.md). Use an appropriately fresh development database when exact seed results are required; never reset valuable data to match a screenshot.

## Independent practice

Find one misleading error and improve its message without exposing internal SQL or secrets. Add a regression test if behavior changes.

## Answer and reasoning

Try the task first. A useful error says what failed and what the user can do, such as removing related enrollments before deleting a course. It should not reveal credentials, stack traces or SQL internals.

## Tutor guidance and self study review

Ask the learner to predict the result before running each step. Demonstrate the worked procedure, then let the learner reproduce it independently. Use the result check as the completion gate. Have each learner explain one decision and diagnose one deliberate mistake. Give support by reducing sample data rather than skipping the concept; use the independent task for further practice.

For self study, close the example and repeat the key action from memory. Reopen it to compare, record the error and fix, then commit the working result. Do not advance simply because code was copied successfully: explain what it does and why the check proves it.
