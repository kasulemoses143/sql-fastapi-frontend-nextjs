## Vocabulary

Flush: send pending SQL without ending the transaction. Commit: complete transaction. Rollback: clear unsuccessful transaction work. Refresh: retrieve current stored values.

## Explanation

A Session tracks pending ORM changes and transaction state. add queues an object; commit flushes the SQL and commits it. refresh retrieves database-generated fields. If the database rejects the write, rollback is required to clear the failed transaction.

Our commit_or_conflict catches IntegrityError only, because duplicates and relationship conflicts are known client-visible state problems. A network outage is a different failure and should be diagnosed in server logs. Catching every exception and returning “duplicate” would hide real problems.

The Session dependency closes its session after each request. The engine may live across requests, but a Session object must not. Good request isolation and database constraints remain necessary under concurrent traffic.

## Worked procedure

1. Keep the Lesson 18 backend running against development PostgreSQL. Open /docs.
2. POST a new student, then POST the same normalized email again. Record 201 followed by 409.
3. Immediately POST a different valid student. Confirm it returns 201.
4. Read commit_or_conflict line by line and trace add → commit → exception → rollback → response. No new application file is needed in this lesson.
5. Use SELECT to confirm there is exactly one row for the duplicated email.

```sql
SELECT email, COUNT(*) FROM students GROUP BY email HAVING COUNT(*) > 1;
```

## Independent practice

Why is checking for an existing email before INSERT insufficient by itself under concurrency?

## Answer and reasoning

Try the task first. Two requests may both observe no existing row, then both insert. A database unique constraint decides the outcome atomically; the loser must roll back and report a conflict.
