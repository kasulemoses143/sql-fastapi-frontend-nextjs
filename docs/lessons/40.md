# Lesson 40 Type checking accessibility and UI failure states

## Learning objectives

Check the reference UI systematically; distinguish compiler evidence from behavior evidence; prepare an integration test plan.

## Before you begin

Pass the preceding lesson's result check. Keep your files in student-project and these notes in course-reference. Complete only the setup sections directed by this lesson. Commit working code before replacing a complete file. A recovery checkpoint creates code in a new folder; it does not copy credentials or initialize database data.

## Vocabulary

Static check: inspect types before execution. Behavioral test: observe real actions. Accessible name: programmatic control label.

## Explanation

A typecheck can catch wrong props, incorrect event types, missing fields and incompatible array updates. It cannot prove that the API is reachable, that CORS is configured or that the database stored a row. A production build adds compilation checks but still needs manual/automated workflow tests.

UI quality includes empty, loading, failure and pending states. A blank table after a request failed should not be presented as “no records.” Users need to know which condition occurred. Status and alert roles help communicate dynamic feedback.

An accessible form has persistent labels, visible focus, keyboard operation and usable errors. A table needs meaningful headings and a caption. These are part of implementation, not final decorative extras.

## Worked procedure

1. In course-reference/frontend run npm run typecheck and npm run build.
2. In your practice form navigate using Tab, Shift+Tab and Enter. Confirm visible focus and that cancel does not submit.
3. Write test cases for empty list, request loading, validation failure, network failure and success.
4. Before integration, identify the expected API URL and which backend origin must allow localhost:3000.

```sh
npm run typecheck
npm run build
```

## Independent practice

Why does a test asserting that a Save button exists fail to establish that saving works?

## Answer and reasoning

Try the task first. It checks presentation only. A saving test must submit valid input, observe the request/result and confirm the persisted record after a subsequent read.

## Tutor guidance and self study review

Ask the learner to predict the result before running each step. Demonstrate the worked procedure, then let the learner reproduce it independently. Use the result check as the completion gate. Have each learner explain one decision and diagnose one deliberate mistake. Give support by reducing sample data rather than skipping the concept; use the independent task for further practice.

For self study, close the example and repeat the key action from memory. Reopen it to compare, record the error and fix, then commit the working result. Do not advance simply because code was copied successfully: explain what it does and why the check proves it.
