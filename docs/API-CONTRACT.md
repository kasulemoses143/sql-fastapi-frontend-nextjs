# Data design and API contract

## Relational model

```text
students                       enrollments                         courses
id PK                  ┌────── student_id FK          ┌────────── id PK
full_name              │       course_id FK ──────────┘           code UNIQUE
email UNIQUE           │       id PK                              title
  id ──────────────────┘       enrolled_on                         credits
                               status
                               UNIQUE(student_id, course_id)
```

Each student and course can have many enrollments. Enrollment is the relationship record. IDs are generated by PostgreSQL; clients must not supply an id on create. All columns in the initial schema are NOT NULL.

| Table | Field | Type and rule |
|---|---|---|
| students | id | integer generated primary key |
| students | full_name | varchar 100, nonblank |
| students | email | varchar 254, unique; API validates address and lowercases it |
| courses | id | integer generated primary key |
| courses | code | varchar 20, unique, nonblank; API uppercases it |
| courses | title | varchar 120, nonblank |
| courses | credits | integer from 1 to 6 |
| enrollments | id | integer generated primary key |
| enrollments | student_id | foreign key to students.id, indexed |
| enrollments | course_id | foreign key to courses.id, indexed |
| enrollments | enrolled_on | date, database default CURRENT_DATE |
| enrollments | status | active, completed or withdrawn; default active |

A student/course pair may exist once. Deleting a referenced parent is restricted. Delete the enrollment explicitly before deleting a student or course. Withdrawal keeps history; deletion removes the relationship. Do not silently cascade parent deletes.

## Boundary between SQL models and API schemas

Handwritten SQL creates the actual PostgreSQL tables. SQLAlchemy models map those existing tables to Python. Pydantic schemas validate requests and serialize responses. They have different responsibilities. Editing a Python model does NOT migrate an existing table. The initial application never calls create_all on startup. A later schema change needs a reviewed incremental migration.

Python string lengths and API fields mirror SQL lengths. Database-generated values are refreshed after commit. Validation failures occur before the route handler (422). Database conflicts are caught at commit and rolled back (409). Missing resources use 404. SQLAlchemy parameter binding and ORM statements keep data separate from query structure.

The schema itself enforces nonblank names, unique emails/codes, valid credits/statuses and foreign keys. Email syntax and uppercase/lowercase normalization are API policies; a direct SQL writer must follow those policies too. For stronger database-wide case-insensitive uniqueness, teach a later migration using a lower(email) index or an appropriate PostgreSQL type, with duplicate cleanup first.

## Endpoint inventory

API paths are at the backend origin root: `/students`, not `/api/students`. There is no extra Next.js API server. All list endpoints support `?limit=100&offset=0`; limit is 1–100 and offset is nonnegative. Results are sorted by id.

| Method | Path | Request | Success |
|---|---|---|---|
| GET | /health | none | 200 status object, no DB query |
| GET | /students | limit, offset query values | 200 array of StudentRead |
| POST | /students | StudentWrite | 201 StudentRead |
| GET | /students/{id} | none | 200 StudentRead |
| PUT | /students/{id} | complete StudentWrite | 200 StudentRead |
| DELETE | /students/{id} | none | 204 empty body |
| GET | /courses | limit, offset | 200 array of CourseRead |
| POST | /courses | CourseWrite | 201 CourseRead |
| GET | /courses/{id} | none | 200 CourseRead |
| PUT | /courses/{id} | complete CourseWrite | 200 CourseRead |
| DELETE | /courses/{id} | none | 204 empty body |
| GET | /enrollments | limit, offset | 200 array of EnrollmentDetail |
| POST | /enrollments | EnrollmentWrite | 201 EnrollmentRead |
| GET | /enrollments/{id} | none | 200 EnrollmentRead |
| PATCH | /enrollments/{id} | EnrollmentUpdate | 200 EnrollmentRead |
| DELETE | /enrollments/{id} | none | 204 empty body |

## Exact JSON examples

StudentWrite: `{"full_name":"Amina Demo","email":"amina@example.com"}`.

StudentRead: `{"id":1,"full_name":"Amina Demo","email":"amina@example.com"}`.

CourseWrite: `{"code":"SQL101","title":"Relational databases","credits":3}`.

CourseRead adds `"id":1`. Credits must be a JSON integer, not a string or fraction.

EnrollmentWrite: `{"student_id":1,"course_id":1}`. Use actual returned IDs; never assume seed IDs are exactly 1.

EnrollmentUpdate: `{"status":"completed"}`. It cannot move an enrollment to another student/course. Delete and recreate the relationship for that operation.

EnrollmentRead: `{"id":1,"student_id":1,"course_id":1,"enrolled_on":"2026-01-01","status":"active"}`. The sample date is illustrative; the real database supplies its current date.

EnrollmentDetail is returned by the LIST endpoint and adds `student_name`, `course_code` and `course_title`. The detail GET returns EnrollmentRead. There is no nested ORM relationship serialization; the list route performs an explicit SQL join.

## Failure contract

422 means invalid body/path/query shape or invalid field values. Duplicate email, duplicate code, duplicate enrollment or a restricted parent delete returns 409 with `{"detail":"Conflict with an existing record or relationship"}`. Missing records, including missing parents during enrollment creation, return 404 with `{"detail":"Record not found"}`. Unexpected database outages are server failures to diagnose in logs, not automatically duplicate conflicts.

The frontend displays validation details or a readable fallback. It must not parse JSON after a 204. Errors should not return SQL, passwords or stack traces to the browser. The current app does not implement login, access control, total counts, server-side search or pagination controls in the UI. Those are explicit extensions, not hidden finished features.
